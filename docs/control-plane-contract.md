# Veyra control-plane contract (draft)

This document defines the intended communication contract for the Veyra local server, dashboard, and receiver agents. The operator setup/session routes, device inventory, receiver pairing, heartbeat endpoints, per-device assignments, receiver configuration polling, assigned-media manifests, and media downloads listed as implemented below exist today. Remote commands, WebSocket messages, and detailed health workflows remain design targets. Treat this as an evolving contract and keep it aligned with tested implementation.

## Design principles

1. The server is the authority for shared device assignments, media, playlists, and operator accounts. Receivers poll versioned configuration and media manifests, and activate only fully downloaded, SHA-256-verified cache snapshots.
2. A receiver is authoritative for what is actually happening on its own display.
3. A receiver must keep playing without an active server connection.
4. NDI discovery and video transport are independent of the Veyra management channel.
5. Every command has an ID, expiry, acknowledgement, and final outcome.
6. Every configuration and media manifest has a version.
7. A failed or partial update must never overwrite the last known-good local state.
8. Device credentials are separate from human operator sessions.

## Connection model

- Dashboard uses authenticated HTTP requests for management operations.
- Dashboard subscribes to a server WebSocket for live device state and operation updates.
- Receivers establish an outbound connection to the local server. The server should not need to initiate arbitrary inbound connections to receiver machines.
- Receivers send periodic heartbeats and playback reports.
- The server sends commands and version notifications over the receiver's persistent channel. Receivers acknowledge commands and report completion or failure.
- If a persistent connection drops, the receiver retries with bounded exponential backoff and continues local playback.

## API versioning

All HTTP routes live below `/api/v1`. WebSocket messages carry an explicit `protocolVersion`. Unknown major versions are rejected with a clear compatibility error; additive optional fields may be introduced within a compatible version.

All timestamps are UTC ISO-8601 strings. IDs are opaque strings generated by the server unless otherwise specified. Management payloads use JSON, except media uploads, which send the raw image bytes with a matching PNG, JPEG, or WebP content type.

The dashboard must not have a route that accepts arbitrary shell commands. Remote actions are a fixed allowlist, initially:

- `set_ndi_source`
- `set_fallback_playlist`
- `request_config_sync`
- `request_media_sync`
- `restart_receiver`

A machine reboot command is intentionally not part of the initial allowlist.

## Receiver enrollment and identity

Implemented first-enrollment flow:

1. An operator creates a short-lived, single-use pairing code in the dashboard.
2. The receiver is given the local server address and pairing code during setup.
3. The receiver exchanges the code for a stable device ID and a device credential.
4. The server invalidates the pairing code after successful use or expiry.
5. The receiver stores its credential with restrictive filesystem permissions.
6. Subsequent connections authenticate as that device, not as a human operator.

The server stores only a verifier/hash of long-lived device credentials where practical. Operators can revoke a credential from the dashboard; a revoked receiver can no longer submit heartbeats. Its record can then be removed before pairing a replacement credential. A receiver must not be able to enroll itself using a predictable device name or unauthenticated LAN broadcast.

The server refuses non-loopback binds without TLS, and the C++ client verifies the certificate chain and hostname. Production still needs a documented CA provisioning process and tested credential rotation/recovery procedures. Being on a LAN is not, by itself, authentication.

## Receiver API

Implemented endpoints:

| Method | Route | Purpose |
|---|---|---|
| POST | `/api/v1/receiver/pair` | Exchange a one-time pairing code for a device ID and device credential |
| POST | `/api/v1/receiver/heartbeat` | Submit a bearer-authenticated heartbeat, current playback state, and optional discovered NDI source snapshot |
| GET | `/api/v1/receiver/config` | Retrieve the versioned NDI source and fallback playlist assignment |
| GET | `/api/v1/receiver/media-manifest` | Retrieve ordered image metadata for the assigned fallback playlist |
| GET | `/api/v1/receiver/media/{mediaId}` | Download an image only when it belongs to the receiver's assigned fallback playlist |

Planned endpoints:

| Method | Route | Purpose |
|---|---|---|
| POST | `/api/v1/receiver/playback` | Report playback/source/fallback transitions |
| POST | `/api/v1/receiver/commands/{commandId}/ack` | Acknowledge a received command and report its result |

The pairing endpoint accepts a short-lived, single-use 12-digit code. The receiver receives its device credential once; the server stores only its HMAC-SHA-256 verifier for pairing codes; the HMAC key is stored separately in a restrictive local file. Heartbeats use the device credential as a bearer token. The C++ receiver client implements one-time pairing, TLS-verified bearer heartbeats, source snapshots, bounded retry/backoff, owner-only credential storage, versioned config and manifest polling, SHA-256-verified media downloads, persistent local cache, and image fallback. Media synchronization runs independently of heartbeat reporting, is cancellable during shutdown, and accepts at most 512 MiB of assigned playlist assets. A failed download does not replace the active manifest; a regression test exercises this rollback path. Corrupted cached files are rejected by SHA-256 verification and can be downloaded again. A new cache snapshot becomes active only after all listed assets are downloaded and verified; the previous snapshot is retained during the transition and obsolete cache files are pruned after a subsequent successful synchronization. It is compiled independently of the NDI SDK in CI; the complete native player still requires an official NDI SDK build and hardware validation.

## WebSocket event envelope

Every event uses a common envelope:

```json
{
  "protocolVersion": 1,
  "eventId": "evt_opaque-id",
  "type": "device.heartbeat",
  "occurredAt": "2026-11-14T10:00:00Z",
  "deviceId": "dev_opaque-id",
  "payload": {}
}
```

Initial event types:

- `device.heartbeat` — receiver liveness, software version, uptime, and reported connectivity.
- `device.playback.changed` — current NDI source, playback mode, fallback playlist, and transition reason.
- `device.health.reported` — bounded diagnostic metrics and recent error summary.
- `config.version.available` — a newer desired configuration is available.
- `media.manifest.available` — a newer assigned media manifest is available.
- `command.created` — a command is ready for the receiver.
- `command.acknowledged` — receiver accepted or rejected a command.
- `command.completed` — command finished with a result.

Events are notifications, not the only source of truth. On reconnect, the receiver fetches the latest full configuration and media manifest; it must not rely on having received every event while offline.

## Device state model

The server should keep separate dimensions rather than one ambiguous online/offline flag:

- **Connection:** online, stale, offline.
- **Playback mode:** ndi, fallback, idle, error, unknown.
- **NDI source state:** connected, unavailable, not_configured, unknown.
- **Server synchronization:** current, pending, failed, unknown.

A device can be connected to the server while its NDI source is unavailable. A device can also be disconnected from the server while continuing NDI playback or local fallback. The dashboard must represent these states independently.

Each device now has a monotonically increasing `configVersion`, an optional exact NDI source name/address assignment, and an optional fallback playlist assignment. The operator API validates that source name/address are supplied together and that the playlist exists. The receiver config endpoint returns a schema-versioned snapshot. The manifest exposes only ordered items from that device's assigned fallback playlist, including SHA-256, byte size, MIME type, duration, and a receiver-only download path. Media download authorization is checked against the device's current playlist assignment on every request.

The current server records last-seen time and derives online at 45 seconds or less, stale after 45 seconds through 120 seconds, and offline after 120 seconds. The heartbeat interval defaults to 15 seconds. These thresholds are currently server defaults rather than operator-configurable settings.

## Configuration and media synchronization

- Server-managed configuration is versioned per device.
- A receiver downloads a candidate update to a temporary location, validates it, then atomically promotes it to active state.
- Media manifests include stable media IDs, content hashes, byte sizes, MIME types, and download locations.
- Receivers verify downloaded asset size and hash before marking an asset available.
- The last known-good configuration and fallback playlist remain active until a complete replacement is validated.
- Media deletion is blocked while an asset is referenced by a playlist or assigned fallback, unless the operator first changes those references.
- The receiver reports which manifest version and assets it has successfully applied.

The initial fallback player supports PNG, JPEG, and WebP image items with explicit order and display duration. Each receiver caches only the assets in its assigned fallback playlist.

## Command lifecycle

A command has:

- Unique command ID.
- Target device ID.
- Allowlisted command type.
- Validated payload.
- Creation and expiry timestamps.
- Status: queued, delivered, acknowledged, running, succeeded, failed, expired, or cancelled.
- Optional bounded result/error details.

Commands are idempotent where possible. Replaying the same command ID must not cause repeated destructive actions. The dashboard displays the command's actual state and must not report success merely because the server accepted it into a queue.

## Security requirements

- Human sessions and device credentials are separate.
- Every management route requires an authenticated operator session and authorization check.
- Every receiver route requires a valid device credential.
- Pairing codes are random, single-use, short-lived, and rate-limited.
- Device credentials can be revoked.
- Uploads are size-limited and validated by content, not only by filename or client MIME type.
- Logs must not contain passwords, session cookies, pairing codes, or device secrets.
- Commands are allowlisted and schema-validated.
- CORS is restricted to the dashboard origin; do not use wildcard credentialed CORS.
- The local server should bind to intended LAN interfaces and document its exposure. A local deployment still needs a deliberate transport-security policy.

## Open implementation decisions

The following still need a technical decision record or implementation:

1. Device credential rotation and recovery after a receiver is reset or loses its token file.
2. Whether the receiver uses HTTP polling plus WebSocket, or one persistent WebSocket channel for live control.
3. Media storage quotas, retention policy, and cleanup of unreferenced files.
4. Whether heartbeat interval and stale/offline thresholds should be operator-configurable.
5. Playlist behavior when an item is missing, corrupted, or cannot be decoded.
6. Production CA provisioning and certificate renewal for multi-receiver deployments.

The SQLite migration mechanism (schema v6), initial pairing flow, TLS requirement for non-loopback binding, media storage, per-device source/fallback assignment, versioned receiver configuration, assigned-media manifests, receiver-authenticated asset downloads, verified local cache, and timed image fallback are implemented. Remote commands and WebSocket events remain in progress. The complete player still needs an official NDI SDK build and target-hardware validation.
